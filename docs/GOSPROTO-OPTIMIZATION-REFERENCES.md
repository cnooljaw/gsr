# 编解码优化参考与适用边界

2026-10-20。本文记录参考文章对 gosproto 的启发，不改变现有 API、官方 wire、所有权或验证预算。Body 与 Packing 两条主线继续，业务协议实验单独记录，不替换原始比较夹具。

## 可以直接指导库内部实现的经验

- [KiteX 性能优化实践](https://developer.volcengine.com/articles/7599493793671053321)：固定协议下，预计算容量、直接写最终缓冲、减少分配、复制与热循环调用值得借鉴。基本类型容器可把多次分配降成一次，但遍历编码本身仍为 O(n)。gosproto 已有类似实现，下一步需测量剩余尺寸计算与写出中的重复字段访问、标量判断、递归和边界检查，避免重复实施已有优化。Thrift 的字段重排不能直接搬到 Sproto 的 tag 顺序规则。
- [Dynamicgo 的 Protobuf 动态反射](https://www.infoq.cn/article/7hSpxsblN3rAIT9PJVxF)：按 schema 操作字节、按路径批量访问，以及直接协议转换可以避免完整中间对象。它的动态消息与普通 Go struct Decode 并非相同输出契约，文章也区分复用模式；不能把其性能比例当作当前 gosproto 的预期。可借鉴类型专门化，但当前公开元数据可变，缓存计划须证明不会过期。
- [Greptime 原文](https://greptime.cn/blogs/2024-04-02-protobuf)：最有价值的是逐层拆开对象构造、嵌套集合复用、通用接口适配和切片操作成本。文中的 Go 对照复用了目标对象，Rust 起点每次创建对象；后续还利用特定输入生命周期并跳过业务不需要的字段。因此标题的差距不是语言或协议的普遍结论。Go string 并不天然零拷贝，是否复制取决于解码器实现与契约。

池化、借用输入、跳过字段、合并子对象分配均须另行核对语义。现有输出独立所有权、子对象独立可达性、失败原子性、GC 写屏障及资源上限不能因参考文章而改变。可以减少重复检查，但必须先证明前置检查覆盖同一不变量；不能删除必要验证换速度。

## 需要业务 schema 配合的优化

| 思路 | 对 Sproto 的价值 | 实验约束 |
| --- | --- | --- |
| 结构数组改为多个标量数组 | 减少子消息头、对象与字段分发，适合密集同构数据 | schema/wire 改变；明确缺失值、空元素、索引对应及列长校验，PB/SP 两边采用相同语义 |
| 时间戳基值加差分 | 原绝对值需要 8 字节、差值可用有符号 32 位时，可能降低整列整数宽度 | 计算 base、恢复和溢出校验计入耗时；测离群值；ID 不一定连续，按真实分布判断 |
| 差值 bit packing | 有明确范围时可进一步缩小 bytes | 属于业务自定义编码；明确位宽、数量、符号与合法长度，计入额外解包成本 |

本地官方参考 `../skynet/lualib-src/sproto/sproto.c` 的 `sproto_encode` 与 `encode_integer_array` 表明：Sproto 标量小非负整数可内联，其余整数使用定宽数据；整数数组采用统一的 4/8 字节元素宽度。它不是 Protobuf 的逐值 varint/zigzag；一个宽值可使整列升宽。差分与列式布局需同时测 Body、Pack、组合路径和最终包长，不能只看未 Pack 长度。

## 贴文中类型建议的边界修正

依据 [Protobuf 官方编码说明](https://protobuf.dev/programming-guides/encoding/) 对 varint 与 ZigZag 的定义，可推导以下边界（只算值，不含字段 tag、集合长度与 presence）：

- 无符号 varint 的 0 仍占 1 字节；公式需补最小值 1。
- 无符号值到 `2^21−1` 才是严格少于 4 字节；`2^21` 至 `2^28−1` 恰为 4 字节。
- ZigZag＋varint 至多 4 字节的区间为 `[-2^27, 2^27−1]`；严格少于 4 字节为 `[-2^20, 2^20−1]`。
- 同一 int32 范围内的数，sint32 与 sint64 的值编码长度相同。不能依据贴文的区间表机械选择 sint64。
- 结构示例按给出的 packed wire 是 22→12 字节，并非恰好减半；收益依赖字段密度与 presence。数据示例最大差值为 16，需要 5 bit；只有最大差值不超过 15 时才够 4 bit。

## 后续实验顺序

1. Body：沿现有 profile 隔离尺寸计算与写出的重复工作，再检查结构字段执行和构造成本；只比较相同输出语义。
2. Packing：继续检查实际 byte pattern 下的扫描、分支、批量搬移和输出分配，验证小包及不同密度的代价。
3. 业务建模：另建行式/列式、绝对值/差值的配对夹具，保留原 benchmark，四种 Go/TS × PB/SP 实现均计入模型转换时间，报告编码长度、组合耗时、分配与持有内存。

收益大小不设固定淘汰线；小收益也保留完整证据，同时公开回退、控制检查和不确定性。本轮仅分析文档，无新性能测量或运行时代码变更。
