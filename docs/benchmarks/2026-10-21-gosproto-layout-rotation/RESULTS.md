# 静态编码调用树摆放轮换

2026-10-21，基线gosproto `2e1d44b`、布局分段候选 `451998e`。前轮静态调用树报告已提交GSR `f842999`，未推送。本轮**确认了函数摆放与同源码控制偏差的相关性，也增加了保留布局分段候选的重复证据**。没有新增生产代码，不把多种摆放混成一个“修正后收益”。

## 实际改变了什么

不增加NOP，不改业务数据或算法，只轮换三棵静态树的定义顺序：

- 012：Baseline → Clone → Candidate
- 120：Clone → Candidate → Baseline
- 201：Candidate → Baseline → Clone

除static_experiment.go的函数定义顺序外，三个归档的其他库/测试/harness Go源哈希相同。每棵树的函数体先做可逆名称替换校验，gofmt后再还原核对原提交，均通过。三种布局先全部构建、完成契约与分配对照，再开始计时。

测量前从实际二进制objdump确认12个Buffer/Message/Field/Record函数相对地址确实改变。下表是Field入口相对ExperimentStaticNormal的偏移，绝非仅切换源文件中的标签：

| 摆放 | Baseline Field | Clone Field | Candidate Field |
| --- | ---: | ---: | ---: |
| 012 | 0x0dc0 | 0x2c60 | 0x4b00 |
| 120 | 0x4f30 | 0x0dc0 | 0x2c60 |
| 201 | 0x3090 | 0x4f30 | 0x0dc0 |

源码顺序改变也会带来编译/链接位置等自然变化。因此结果支持“摆放相关”，不能进一步唯一归因为指令缓存、分支预测或某一个地址模数。

## 大型消息结果

负值表示B耗时降低，控制不相减。所有百分比都是该布局独立计算的原始值，不是布局间平均或扣控制后的值。

| 摆放/入口 | clone中位 / IQR pp | 候选第1轮中位 / 累计 | 第2轮中位 / 累计 |
| --- | ---: | ---: | ---: |
| 012 Encode | +4.93% / 0.51 | −1.99% / −3.36% | −2.08% / −2.65% |
| 012 PEncode | +2.74% / 1.78 | −0.78% / −0.38% | −1.71% / −2.70% |
| 120 Encode | +0.44% / 1.90 | −1.90% / −1.61% | −2.09% / −0.24% |
| 120 PEncode | +0.21% / 2.12 | −1.98% / −3.47% | −2.11% / −2.63% |
| 201 Encode | +0.37% / 1.99 | −1.79% / −1.77% | −0.80% / +0.62% |
| 201 PEncode | −0.17% / 0.84 | −1.08% / −0.90% | −1.51% / −1.13% |

原摆放012的clone约5%中位偏差复现，另外两种接近零。这解释了为什么“源代码相同”仍不能直接假定控制为零；但本轮没有分离编译位置、调用环境及硬件状态的单一根因。

候选大型Encode的6次中位比较全部改善，范围0.80%～2.09%；其中201第二轮累计反慢0.62%，仍保留。大型PEncode的6次中位和累计全部改善，中位范围0.78%～2.11%。这比单一摆放更支持保留候选的小幅业务收益，也不意味着每个百分比都能精确归给布局游标操作，或保证其他机器相同。

不设置5%最低收益门槛，也不因控制偏差而把所有小收益一概丢弃；同样不把012的4.93%从候选中减掉来制造更高收益。

## 代价和覆盖范围

7项短数组仍有代价，不能只列大型收益。012的Encode中位慢1.48%/1.44%，201慢2.04%/1.66%；120首轮慢8.29%、次轮快0.09%，该较大反向也完整保留。各布局的7项PEncode中位均慢。实际小型消息多为接近零的混合方向，未宣称全消息胜出。

前置31项数组的Encode在3种摆放×2轮中位和累计全部改善，支持跨local/extra布局处的收益。纯整数数组没有进入这条记录数组路径，其波动不作为分段读取的直接收益，候选整体也不承诺无间接回退。

本轮定向选择5条消息×Encode/PEncode：实际大小游戏、整数数组控制、7项短数组、前置31项布局边界。没有重测旧20项的所有形态；AddressBook、ASCII及8/33/128项单独数组仍以此前报告为证，不能说本轮重新覆盖。正确性层仍沿用91组边界差分和既有契约，覆盖这些长度。

完整结果分开保存：[012](012/ALL-CASES.md)、[120](120/ALL-CASES.md)、[201](201/ALL-CASES.md)。40项（含self/clone）中位/累计反向数分别9、9、13，全部保存；不跨布局池化或挑选最好的一轮。

## 验证与方法

三次准备各23条日志流程，共69条成功；120个测量进程全部成功。总计720轮、2880组ABBA/BAAB、11520块。实际函数地址变化在测量前断言通过；三种布局按mode/case交错，避免把一种布局全部测完后才测下一种。

每布局计时前：三模式边界/预算/元信息/ownership的race/checkptr、代表消息wire/padding、正常入口AllocsPerRun分配对照、harness vet、10项输出预检通过。测量后所有库/输入/生成物/二进制哈希再核对；gofmt后函数体还原通过。各布局大型消息保持正常入口的3968B/2allocs量级，累计微小尾数保留，没有旧内部选择器额外布局分配。

GOMAXPROCS1/GOGC100/GOMEMLIMIToff，50ms每臂预热，256次baseline调用校准20ms目标块。每进程6轮×4组四块，全部GC、暂停、heap和分配数据保留。候选实际块4.053～68.213ms，不按块长/GC过滤。准备脚本最初因plan字段名重复发生一次Python语法错误，尚未运行Go构建或任何采样；改为treeOrder后完成以上流程，不存在丢弃测量样本。

本轮没有新生产实现，未重复全库/fuzz/oracle/GoTS；451998e的完整验收仍有效。正式依赖仍v0.4.0，真实库七项用户删除保持，未推送/发布。

## 结论与下一步

保留451998e布局分段候选的理由更充分：正常分配已经确认，关键大型/组合路径在多种实际摆放下方向重复；短数组与长尾代价也明确保留。后续报告用具体消息和实测范围描述，不写一个统一提速百分比。
