# 编码布局项数与按需增长诊断

日期：2026-10-18。库基线 `a161158`，GSR 基线 `d6c672c`，均已本地提交，未推送。此轮只做诊断，没有生产候选、CPU A/B 或 PB/TS 新排名；Decode 冻结，正式依赖仍为 v0.4.0。

结论：`game_large` 的 512 B 是一次必要的布局外溢分配，不是整块浪费。真正值得实验的是长数组累计扩容；减小初始容量会让当前大型消息多一次分配。先保留初始 128 项，后续单独评估按需增长策略。

## 1. 方法与可复现边界

- 从已提交库归档两份源码。`before` 仅改 module 路径，保留全部 Go 源码；三个分配入口全部调用它。
- 另一份归档只增加 [诊断 helper](layout-hook.go.txt)，复用原 `encodedSize`，读取最终布局并用原 `add` 回放增长点。成功时再用同一份布局写出，核对全部记录被消费、wire 与未插桩基线一致。helper 不进入库工作树或正式 API。
- [固定计划](plan.json) 覆盖 6 个已有/短文本输入、19 种长度 × 3 种 full/nil/half 记录、19 种含整数数组的记录数组、16 种嵌套形态、7 种链深度、4 种预算失败：共 **109 项**。
- 未插桩基线分配观测 **317 个入口 × 128 次 = 40576 次**，构造、schema/RPC 预热和显式 GC 均在计数外。成功输入测 EncodeWithLimits、EncodePacked、RequestEncode+CancelSession；预算失败只测显式 Limits 的原始 body 入口，不假设存在公开的 EncodePackedWithLimits。
- Go 1.24.13 / darwin arm64 / Apple M2，GOMAXPROCS=1，GC 默认启用。没有 CPU 计时，`commands.json` 的墙钟耗时只用于复现诊断。
- 第一阶段完成后固定 [独立增长模型计划](model-plan.json)：原观测的 48 个不同项数 × 4 种策略 × 128 次 = **24576 次**。仅比较布局分配，不改变生产代码，不作为 API 加速结果。精确容量是事后已知最终项数的理论参照，不能在原预检第一次外溢时直接获得。

原始数据在 [raw.json](raw.json)、[model/model.json](model/model.json)，独立核对汇总在 [summary.json](summary.json)。无分配尾差；没有删除失败输入或重跑来筛选结果。

## 2. 当前大型消息到底用了多少

`game_large` 有 128 个 Item、根 GameState、两个非空整数数组宽度：**131 项 = 栈内 32 + 外溢 99**。

| 内容 | 项数/字节 |
|---|---:|
| 根结构头项数 | 1 项，值 12 |
| 两个整数数组宽度 | 2 项，值 4 |
| Item 头项数 | 128 项，值 3 |
| 外溢实际数据 | 99 × 4 = 396 B |
| 当前外溢容量 | 128 × 4 = 512 B |
| 请求容量内未用部分 | 116 B |
| 事后精确容量模型实际 TotalAlloc | 416 B |
| 相比当前可节约的分配计数 | 96 B，仍为 1 次 |

原始 Encode、EncodePacked、真实请求入口均为 **3968 B / 2 次**；其中输出分配计数 3456 B，布局 512 B。各入口返回的 len/cap 不相同，原值均保留，不能混淆 Go 分配计数与 API 返回容量。

精确模型仅省总分配的约 2.4%，不能把整块 512 B 当作可直接消除的浪费。改小初始容量也不成立：

| 布局总项数 | 当前初始 128：B/次 | 初始 64：B/次 |
|---:|---:|---:|
| 33 | 512 / 1 | 256 / 1 |
| 65 | 512 / 1 | 256 / 1 |
| 97 | 512 / 1 | 768 / 2 |
| **131（game_large）** | **512 / 1** | **768 / 2** |
| 161 | 1536 / 2 | 1792 / 3 |

这里 B/次均只指布局累计分配，不含最终输出。初始 32 的增长轨迹也保留于 raw 的 InitialGrowth；未额外测它的分配或 CPU。

## 3. 真正会积累的部分

当前切片 cap 序列在本机为 `128 → 256 → 512 → 864 → 1344 → 2048 → 3072 → 4096 → …`，最终容量不能代表累计分配；旧缓冲的复制与后续回收也不能忽略。

| 消息形态 | 布局总项数 | 外溢项数 | 最终外溢 cap | 布局累计 B / 分配次数 |
|---|---:|---:|---:|---:|
| full 256 记录 | 257 | 225 | 256 | 1536 / 2 |
| full 512 记录 | 513 | 481 | 512 | 3584 / 3 |
| full 1024 记录 | 1025 | 993 | 1344 | 12416 / 5 |
| full 4096 记录 | 4097 | 4065 | 4096 | 49280 / 8 |
| 32 组 × 128 记录 | 4129 | 4097 | 5440 | 71040 / 9 |
| 4096 个含整数数组的记录 | 8193 | 8161 | 10240 | 140672 / 11 |

full/nil/half 同长度使用相同布局项数：nil 记录也有零头项数，不能通过漏记 nil 来换取分配下降。小包仍只使用现有栈内 32 项，不扩大栈。

## 4. 按需倍增值得实验，但模型已显示代价

模型保持初始 128，只有外溢区用尽时才按 2 倍分配并复制；不读未来长度、不提前按 MaxElements 预分配。

| 布局总项数 | 当前：累计 B / 次数 | 倍增：累计 B / 次数 | 当前 → 倍增最终 cap |
|---:|---:|---:|---:|
| 131 | 512 / 1 | 512 / 1 | 128 → 128 |
| 1025 | 12416 / 5 | 7680 / 4 | 1344 → 1024 |
| **1057** | **12416 / 5** | **15872 / 5** | **1344 → 2048** |
| 4097 | 49280 / 8 | 32256 / 6 | 4096 → 4096 |
| **4129** | **71040 / 9** | **65024 / 7** | **5440 → 8192** |
| 8193 | 140672 / 11 | 65024 / 7 | 10240 → 8192 |

1057 项对应真实构造的 32 组 × 32 记录，累计多 **3456 B**；4129 项累计虽下降，最终容量仍增大 **2748 项 / 10992 B**。两项代价完整保留。不能因 4096 记录模型省 17024 B、少 2 次分配，就宣布端到端更快或默认保留倍增。

## 5. 预算失败必须继续按已访问内容分配

| 4096 条记录输入的限制 | 失败时布局项数 | 已消耗元素预算 | 实际 B / 次数 |
|---|---:|---:|---:|
| MaxElements=1 | 1 | 1 | 0 / 0 |
| MaxBytes=2 | 2 | 4098 | 0 / 0 |
| MaxDepth=1 | 1 | 4097 | 0 / 0 |
| MaxBytes=2500 | 80 | 4334 | 512 / 1 |

所有返回均为 nil 输出与 ErrLimit 对应文本；深度 65 的链也按默认深度预算失败。失败布局可能仍含未回填的头项占位，Histogram 仅记录当时状态，不能当作成功 wire。

`budget.add(array.Len())` 已接纳整个数组的元素数，并不代表其逐项深度、字段、整数范围、字节预算均已通过。直接按已知数组长度或剩余 MaxElements 预分配，会使原本 0 分配的早期失败提前分配大块内存；本轮不采用这种捷径。
