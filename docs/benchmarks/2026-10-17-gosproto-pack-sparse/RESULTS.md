# 稀疏 word Pack 筛选与 A/A 诊断

2026-10-17。上一轮已本地提交为 gosproto `bba3326` / GSR `a27ec4e`，未推送/发布。**本轮稀疏 word 候选未通过预设门槛，未采用；独立库工作树保持干净，全部源码仍为 `bba3326`。** 该轮诊断记录已本地提交为 GSR `8f0003f`。Decode 继续阶段性冻结，正式依赖仍为 v0.4.0。

## 定位与候选

从当前基线另采大型、896 项整数数组的 Pack/PEncode 四份有限 CPU profile，见 [baseline-profiles.json](baseline-profiles.json)。普通 word 分类、稀疏字节提取与混合写出仍可见，Pack 还包含分配/GC 成本。runtime.kevent 占约 19%～31%，未归入业务成本。源码行上的样本可能落在分支、调度后的指令或返回附近，不能据此认为 return 本身昂贵，也不把 flat/cumulative 份额相加推导预期加速。

核对本地固定官方 sproto.c 的 pack_seg / sproto_pack：官方逐字节识别非零位并维护 FF 状态。GSR 库当前已用 mask 分类，本轮仅利用“至多两个非零字节”的既有事实，将通用提取循环展开为最多两次固定目标位置写出。没有新增表、零段扫描或 unsafe；混合 word、FF、部分尾块、输出容量公式与所有权保持不变。候选补丁见 [unroll.patch](patches/unroll.patch)。没有更改正式库。

计时前确定的 [gate.json](gate.json)：大型或整数数组 Pack 至少快 5%，对应 PEncode 至少快 2%；其他业务 PEncode 和 Echo 完整帧不得回退超过 5%，分配不增加；明显短包代价可直接撤回。不因结果接近而降低门槛。

## 三轮候选筛选

Apple M2、Go 1.24.13 darwin/arm64、GOMAXPROCS=1、PB v1.36.1。同进程加载 `bba3326` 归档和候选，每项固定 60000 次，按轮反转先后顺序。五组业务、四档 Echo、66 种密度/FF/零段/尾块控制，共 191 项 × 三轮 = **573** 个样本。每轮执行原夹具检查并比较 packing wire。[unroll.json](unroll.json) 与 [raw](raw/) 保留全部原值。以下为本组中位数，µs/op：

| 消息 | Pack 前 → 后 | 变化 | PEncode 前 → 后 | 变化 |
| --- | ---: | ---: | ---: | ---: |
| AddressBook | 0.1333 → 0.1203 | -9.8% | 0.6805 → 0.6474 | -4.9% |
| 小型游戏 | 0.3167 → 0.2864 | -9.6% | 1.0610 → 1.1780 | +11.0% |
| 大型游戏 | 2.8480 → 2.6760 | -6.0% | 9.3890 → 9.1980 | -2.0% |
| 896 项整数数组 | 2.6290 → 2.4760 | -5.8% | 5.3440 → 4.6970 | -12.1% |
| 4 KiB ASCII | 0.6562 → 0.6212 | -5.3% | 1.3040 → 1.2390 | -5.0% |

所有 SP 项分配字节数和次数与本组基线相同。但小型 PEncode +11.0% 超过门槛；FF 4096 B Pack +13.0%、FF 2048 B +7.6%、短密度 n8_32 +5.4%，原值全部保留。候选撤回，没有进入五轮正式验收，不以纯 Pack 收益覆盖组合代价。

控制也出现差值：未改的大型纯 Encode 7.220 → 6.526 µs（-9.6%），ASCII payload -9.1%。整数数组 PEncode 的逐轮差值从 -16.1%、-12.1% 到 -2.2%；不把中位数 -12.1% 宣称为已确认的工程收益。

## 另做一次 A/A 诊断

为判断当前方法的分辨能力，候选撤回后另建不含改动的基线二进制：两份库全部根目录 Go 源码逐字节一致，只改其中一份 module 路径以同进程加载。只采业务 Packing/Echo 的 59 项 × 三轮 = **177** 样本，不重试候选，不与候选中位数混合。[baseline.json](baseline.json) 保存全部原值。

| 相同源码的 A/A 项 | before → sproto（µs） | 差值 |
| --- | ---: | ---: |
| 大型纯 Encode | 6.583 → 7.835 | +19.0% |
| 整数数组 Pack | 3.393 → 2.612 | -23.0% |
| ASCII PEncode | 1.364 → 1.243 | -8.9% |
| 小型 PEncode | 1.059 → 1.045 | -1.3% |

大型纯 Encode 三轮分别为 6.631 → 6.476、6.583 → 9.556、6.517 → 7.835 µs；整数数组 Pack 分别为 3.393 → 2.612、3.692 → 2.622、2.567 → 2.612 µs。只反转一轮顺序和固定 60000 次，未充分消除这些差值。

[assembly.json](assembly.json) 核对该 A/A 二进制的两份 Pack：均为 640 条反汇编指令。归一化私有包名和函数内分支地址后，仅 ADRP 的 PC 相对位移不同，解析到同一个绝对目标页。没有不同 Pack 算法可以解释 A/A 的 23%；尚未区分环境负载、执行顺序、频率/缓存和代码位置等因素，不能只凭这一次诊断确定原因。

**这组 A/A 已不足以支撑约 6% 的候选收益判断。** 它也不能证明候选的小型 PEncode +11% 全是噪声，因此不作为重新通过门槛的理由。旧记录继续保留，但后续小幅优化应先提高测量稳定性：优先建立同一调用目标的 A/A 控制、平衡各轮先后、加长单项测量和分块交错采样，在控制差值可接受后再比较候选。当前未实施新的计时框架，没有新的 PB/SP 总体排名。

## 验证与范围

候选先运行现有 TestPack / TestPackZeroRuns / TestPackPartialRunAtBlockLimit，通过（0.567 秒），覆盖全部 mask、高位字节、FF 边界、输入偏移与零段/尾块；无需为相同 wire 契约再搭一套测试。未新增测试或采用生产改动，因此未重复完整库/race/checkptr/官方 C/Lua/fuzz、GSR/GoTS 或 TS 性能验收。

[validation.json](validation.json) 保存测试命令及当时源码指纹、正式库与归档一致检查、两个归档/补丁复现副本的完整 Go 源码、七份 harness 和三份夹具核对。候选计时、A/A 和 CPU profile 分别绑定各自完整快照；全部 SP 分配控制相同。TS 和夹具核对未变。官方源码只阅读并核对既有固定指纹，没有重跑 oracle。原始 profile/二进制留在忽略目录，摘要和指纹入库。

## 复现与当前状态

```sh
python3 docs/benchmarks/2026-10-17-gosproto-pack-sparse/reproduce-pairs.py \
  --library /path/to/gosproto --output /tmp/gsr-pack-sparse --candidate unroll
```

--candidate baseline 重跑独立 A/A 的 59 项三轮，默认 unroll 重跑 191 项三轮；--prepare-only 只重建与核对，不修改传入库。固定输入见 [inputs.json](inputs.json)。共保留 750 个配对样本和四项独立 CPU profile，不保证复现相同耗时。

正式库保持 `bba3326`，Decode 阶段基线、公开 API、wire、输出容量、预算与所有权不变。下一步优先校准测量方法，暂不堆叠更多普通 Pack 微调。该轮记录已本地提交为 GSR `8f0003f`，未推送/发布，GSR 正式依赖仍为 v0.4.0。
