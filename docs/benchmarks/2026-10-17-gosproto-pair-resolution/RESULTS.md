# GC 边界探针与聚焦校准

2026-10-17。上一轮配对工具和记录已本地提交为 GSR `f064584`，未推送。本轮只扩展工具观测与精确筛选，**没有修改 gosproto 生产代码、恢复候选或调整控制门槛**；独立库仍为 `bba3326` 且工作树干净，Decode 继续阶段性冻结。本轮工具改动与记录已本地提交为 GSR `3a88564`，正式依赖仍为 v0.4.0。

## 16 B 差值的可验证机制

检查当前完整帧的调用路径，Sproto package 前缀编码长度为 6 B。Go 1.24.13 的 tiny allocator 将小型无指针对象合并到 16 B 块，mcache.releaseAll 清空 tiny/tinyoffset；GC 边界可能留下部分使用的块。MemStats 的 TotalAlloc 记录底层分配字节，不能假定相同调用数每个窗口都完全相同。参考源码版本与指纹见 [validation.json](validation.json)。

用隔离 [探针](allocation-probe.go.txt) 固定 128 次 make([]byte, 6)，保留输出，改变显式 GC 的插入位置；先预热 GC，另测不分配的空窗口。它只用于分配机制诊断，不记录性能分数，也不把强制 GC 加到正常采样块。

| 128 次调用的条件 | 总分配字节 | 对象数 | 窗口内完成 GC |
| --- | ---: | ---: | ---: |
| 空窗口，无 GC | 0 | 0 | 0 |
| 空窗口，中间 GC | 0 | 0 | 1 |
| 6 B 分配，无 GC | 1024 | 128 | 0 |
| 完成 63 次分配后 GC | 1040 | 128 | 1 |
| 完成 64 次分配后 GC | 1024 | 128 | 1 |

三轮条件结果一致，见 [allocation-probe.json](allocation-probe.json) 与 [日志](allocation-probe.log)。初稿把 GC 插入索引误标为 calls；修正记录字段为 calls=128、gcBeforeIndex 后重跑，条件和字节结果未改变。

这验证了仅改变 GC 边界就能产生 16 B，也就是 16/128=0.125 B/op 的差值。标准 testing.BenchmarkResult 的 B/op 使用整数除法，这种小数不会出现在常规整数输出中；本工具仍保存精确计数，没有截断后为控制过门。

本轮实际 ASCII 完整帧的 self 窗口也出现：无 GC 时 1870848 B / 640 对象，部分完成一次 GC 的窗口为 1870864 B / 640 对象。clone 中也存在完成一次 GC 却不增加字节的窗口，与“具体边界影响 tiny 块”的机制相符。不能逐组还原上一轮未记录的 GC 时点，也不把每一个微小差值都自动归给同一原因。总控制的分配一致要求保持不变。

## 工具改动与固定实验

- 新增精确 --case 筛选，拒绝未知/重复名称，保留原矩阵顺序；--block-ms 可选 10/40，默认仍为 10。
- 计时区间外用 runtime/metrics 记录前后完成 GC 周期之差；分配窗口另存 NumGC 差，原始结果记录实际 GOGC。拒绝显式关闭 GC 的环境。
- 单列 timingAccepted，方便区分计时离散与分配差值；controlAccepted 仍要求原计时门槛和分配统计同时通过，没有豁免。
- 增加采样参数、生成类型、工具及输入指纹核对。所有含 GC 的样本保留，未增加池、输出复用或生产 API。

计时外读取的周期差覆盖略宽于计时区间的观测窗口，它不是暂停时长，也不能换算为 GC 耗时。观测本身可能影响运行状态，因此新版 40 ms 与旧版 10 ms 是不同实验，不能单独把差值归因于块长度。

计时前写入 [plan.json](plan.json)：只做一次 40 ms self/clone，选择上一轮至少一类控制未通过的 10 项，加大型/整数数组 Pack 两项参照，共 12 项；门槛仍为中位差 ≤2%、IQR ≤3 pp、至少五轮差值 ≤5%、分配中位数相同。不重试到通过，不合并旧轮通过项宣称新的全矩阵通过。

## 40 ms 结果

Apple M2、Go 1.24.13、GOMAXPROCS=1、GC 开启。self 约 50.25 秒、clone 约 46.65 秒，均在原 90 秒限制内；未发生超时或增加运行预算。self 计时控制 2/12、总控制 1/12；clone 两者均为 4/12。双类计时与总控制均只有整数数组 Pack 一项通过。

self 的 ASCII 完整帧计时控制通过，但因 0.125 B/op 的分配中位差，总控制仍为未通过。这正是单列状态的用途，不把“计时通过”改称“总控制通过”。

两类实验共 2304 个计时块，每个块的观测窗口都有完成 GC 周期；没有可用于直接比较的无 GC 块，也没有据此删除全部数据。大型 Pack 的 self 各轮 GC 数约为 A 133～135、B 133～136，仍出现近 10% 的轮次差值。周期计数不能解释全部墙钟波动，不能直接断定 GC 是这些差值的唯一原因。

**40 ms 没有使这些项目整体稳定，未建立更可靠的新性能基线。** 默认目标保持 10 ms；本轮未重跑新版默认配置的 19 项，也不将旧版 10 ms 的 9/19 结论自动赋给新版。原稀疏候选仍撤回，本轮没有 compare、PB/TS 性能或新的优化排名。

## 验证与复现

[validation.json](validation.json) 及 [checks](checks/) 保存验证证据：

- 精确筛选和计时/分配分开报告的用例先在错误/旧实现上失败，修复后通过。Go 新增未知/重复名称、矩阵顺序和显式 GC 观测保护；原统计及固定 wire 用例继续通过。
- Python 共八项通过，新增状态不豁免分配拒绝，以及非法块时长、重复选择、关闭 GC 在准备前被拒绝的检查。实现中的一次文本替换误把 CLI 校验插入纯汇总函数，已有用例立即检出，修正后通过；未进入计时。
- 新 harness 的 go vet 通过；self/clone 两个 prepare-only 副本重建出相同库、harness、夹具、工具和生成类型指纹。
- 正式库源码与 bba3326 一致且工作树干净。未采用生产改动，没有重复完整库/race/checkptr/官方 oracle/fuzz、GSR/GoTS 或 TS 性能验收。

每个模式保存 inputs/commands/raw/summary.json，另有完整合并 [joined.json](joined.json)。共 24 个项目对、144 个配对轮次、2304 个计时块，以及独立的 18 个分配探针窗口；预热/校准和分配窗口不混作计时块。编译副本及二进制仍留在忽略目录。

```sh
python3 docs/benchmarks/2026-10-17-gosproto-pair-resolution/reproduce.py \
  --library /path/to/gosproto --output /tmp/gsr-pair-resolution
```

先核对工具、夹具和生成类型，再按固定计划顺序运行两类校准，最后在独立模块运行分配探针；不修改传入库。输出目录必须不存在，不保证复现相同耗时或控制通过数量。旧报告的复现需取回对应历史工具版本。

本轮确认了分配窗口差值的一种具体机制，也确认了继续单纯拉长块时间不能替代稳定的测量条件。保留新增观测和严格判定，暂不增加更多采样参数或普通 Pack 微调。本轮已本地提交为 GSR `3a88564`，未推送/发布，正式依赖及 Decode 阶段基线不变。后续见 [墙钟与进程 CPU 诊断](../2026-10-17-gosproto-pair-cpu/RESULTS.md)。
