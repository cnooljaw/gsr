## 单一候选

普通mask已排除0/FF，在原固定八字节目标视图中，将按mask清位结束的`src[used]`循环改为：

```go
used := bits.OnesCount8(header)
mask := header
for _, value := range src[:used:used] {
    index := bits.TrailingZeros8(mask) & 7
    dst[index] = value
    mask &= mask - 1
}
src = src[used:]
```

每个有效bit恰对应一个连续源字节，因此循环执行次数与原逻辑相同。完整首遍仍先验证全部packed边界、精确输出尺寸和预算，原错误优先级/零段/FF批量复制不动；输出仍是本次make清零的独占、精确容量切片。无新API、unsafe、池、复用缓冲或公开契约变化。

官方C的sproto_unpack同样按mask消费连续输入，FF走memcpy；普通分支扫描8个位并显式写零，依赖C指针和调用方缓冲。此次只是Go局部循环候选，不是官方要求的实现方式，不借机删除完整预检或改变输出所有权。只读参考及哈希见reference.json。

固定密度对照把同一种word重复512次；它不能代表实际消息中mask位置与密度不断变化的顺序。现有大型消息虽有很多4～6字节word，也不能据此把固定密度收益按比例加权推算业务加速。本轮没有隔离混合顺序、具体mask位置和额外计数的各自成本，尚不能断言退化完全由popcount或分支预测造成。

## 汇编与得到的结论

ARM64机器字行（含填充）388→396，栈112B不变；panicIndex静态点4→3、panicSlice* 10→12。循环中的源索引检查确实消失，但每word引入源窗口和后续推进检查，外加一次有效字节计数。当前Go1.24.13的OnesCount8内联为bits.go的表读取，能看到地址构造和依赖header的MOVBU，不是凭函数名就假设成单条硬件popcount。

这证明“每字节少一次检查”不自动等于总成本下降；同时也证明固定密度下的正向并非应一概忽略。当前证据不支持通用替换，也不支持立即按密度分流：后者仍要计数，且真实混合输入尚未获益。候选保留为实验源码，不落生产。

下一步先补以实际packed流为依据的混合mask对照：区分同一个mask、同密度不同位置、相同mask直方图的原顺序/分组顺序，保持恢复字节数和数据不变，确认循环控制与访问模式的敏感性。只改变合成诊断对照，不替换原业务夹具或把重新排序后的输入当业务排名。再决定是否存在不重复计数的源读取表示；不盲目重做旧查表解包或堆叠密度分支。Body Decode仍开放，Packing继续独立推进。

## 过程与验证

在同一5360fe0归档中增加baseline/clone/candidate适配函数，同一模块、同一进程、共享分配器和Decode。clone去除名称/空白后与基线函数体相同。组合解码为选定UnpackWithLimit(default预算)+公开Decode，等价于当前DecodePacked的两步数据流；为注入候选没有直接调用DecodePacked。实验适配器不进入生产，绝对耗时不作为公开API或PB新排名。
