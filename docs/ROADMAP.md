# 后续工作与范围

已发布能力与迁移见 [发布说明](releases/v1.0.4.md)，当前契约见 [API](API-DESIGN.md)，测试证据见 [验证覆盖](validation/COVERAGE.md)。这里仅记录尚未完成的范围，不重复已完成的实施步骤。

## 接入前按场景验证

| 范围 | 需要补充的证据 |
| --- | --- |
| 真实业务容量 | 目标机器上的 Handler、数据库、日志与 Timer 组合负载；持续时长、延迟和拒绝率由业务确定 |
| 跨机器与部署 | 网络分区、延迟与断线组合、进程信号、磁盘配额、日志采集及告警 |
| Gate | 目标部署的连接容量、长期慢客户端与故障组合、独立密码协议审查 |
| 数据库 | 真实 MySQL / Redis 环境的权限、连接池、超时、事务及恢复 |
| 客户端 | 浏览器、Laya、Cocos；Sproto TS 的完整 int64/BigInt、double 和 binary 组合由独立 gosproto 项目推进 |

## 有实际调用者后再裁决的能力

动态 Discovery 与路由更新、Cluster 认证、多监听、监督与自动重启、Snapshot、服务迁移及持久化投递尚无通用实现。引入前先明确 owner、接纳与失败语义、资源上限、关闭和验证方式。

Core 保持本地消息、串行 Service、Scheduler 和 Timer 边界。业务事务、顺序、幂等、补偿、重试及资源过期判断继续归业务；不为了并行处理引入手工 Reply、业务 goroutine 或隐式来源。
