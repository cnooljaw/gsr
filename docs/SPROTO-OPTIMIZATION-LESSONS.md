# Sproto 性能优化经验：从 TypeScript 到 Go

状态：2026-10-16，TS 性能优化阶段基本完成，后续重点转向 gosproto。本文整理已经验证的做法、撤回的尝试和测量规则，作为 [Go 优化方案](RFC-GOSPROTO-PERFORMANCE.md) 的实施输入；不新增 API、wire 或所有权裁决。

## 1. 阶段结论和基线

TS 当前实现与第五轮验收已提交为 GSR `9801808`。在既定 Node.js 参考客户端、五种代表性消息的原生 pencode/pdecode 上，十项耗时中位数均低于同次 Protobuf；最终 250 项、1250 个计时样本中没有 SP 项中位数回退超过 10%。9560 组新旧差分、20 组官方 C/Lua 向量与 Go/TS Plain/MAC 集成 7/7 通过。详细范围见 [第五轮验收](benchmarks/2026-10-15-sproto-round5/RESULTS.md)。

这足以支持当前阶段收尾，不能扩展成“所有 Sproto 输入都快于 PB”。未验证浏览器、完整客户端吞吐和所有协议类型；Node/V8、对象模型和调用入口都是结果的一部分。默认不再为几个百分点反复改写 TS 热循环。出现真实业务热点、新支持类型、正确性缺陷或明确资源问题时，再以对应输入重开切片。

后续必须区分三份基线：

| 基线 | 当前含义 | 后续用途 |
| --- | --- | --- |
| TS Sproto | GSR `9801808`；最近验收 Node 23.11.0 / V8 12.9 | 固定实现作为控制，不随 Go 优化一起修改 |
| 正式 Go 依赖 | `github.com/cnooljaw/gosproto v0.4.0`；GSR go.mod 未升级 | 保留正式版本对照与发布边界 |
| 后续 Go 实施起点 | 独立 gosproto 提交 `6012b06533657721aff66e1ea16ab158153f6e44`，已包含后续两轮优化，尚未发布 | 从当前源码重建 Go PB/SP 基线和 profile，再做增量 |

Go 不是仍停留在“只保证正确”的初版。已落地最终缓冲直写、预检布局复用、类型化数组/optional 标量、有界 tag 索引和混合 word packing。不能重做已完成的工作，或把当前结果与更早版本相减来归因新收益。最近 Go 证据见 [第二轮结果](benchmarks/2026-10-15-sproto-round2/RESULTS.md)；下一轮仍需重新绑定当前源码与工具链。

## 2. 性能优化不能改变的契约

| 边界 | TS 中保护的内容 | Go 后续需要额外注意 |
| --- | --- | --- |
| 官方 wire | raw/packed 固定向量、FF 最多 256 word、六/七字节合并、尾部补零、未知字段消费 | 保留全部既有类型和字段演进语义，不靠重写夹具签名过关 |
| 数值语义 | boolean、混合正负整数数组、4/8 字节宽度、JavaScript 安全整数范围 | 完整 int64/uint64 边界、窄化拒绝、命名类型、double 原始位模式不能由 TS 安全整数样本替代 |
| 预算与失败 | 编码/解包额度、package 与 body 独立额度、错误后可继续使用实例 | 默认及自定义字节/深度/元素预算、schema 失败回滚、解码失败保留目标原值 |
| 输出所有权 | encode/pack/unpack 的公开结果独占；后续调用不覆盖旧结果 | 不共享上条消息的 optional 指针、字符串/数组或子结构，不返回内部可变工作区 |
| 缓冲生命周期 | 同步私有解包工作区最多保留 16 KiB，大包仅调用内临时使用 | TS 的容量不是 Go 新默认值；任何复用需解释 owner、并发、释放和保留上限，不能机械加池 |

TS 并未验收 Go 库支持的全部 schema、double 或整数范围。可迁移的是边界意识和验证方法，不能把 TS 的覆盖数量当作 Go 覆盖证明。

## 3. 先保证正确，再建立性能排名

最早探针发现 boolean 和混合正负 int64 数组错误。只测字符串或自身 Encode→Decode 往返，会让两个相互配合的错误蒙混过关。先用独立官方 raw/packed 向量复现，再修复，再纳入排名。未知 body 字段未消费导致后续字段错位，以及融合 scratch 挤占原 body 预算，也都先建立回归再修复。

固定官方仓库与版本，分别验证编码字节和解码语义。当前官方快照自身有已记录的部分 64 位 C 解码缺陷，不能为了与错误结果一致而修改正确 wire；参考 [官方兼容记录](SPROTO-INTEGRATION.md)。旧实现只适合作为重构差分的一方，不自动等于规范。

旧实现差分、独立官方向量、跨语言集成承担不同职责。9560 组通过不代表输入穷尽；Go 仍应复用自己的完整回归和有限 fuzz。

## 4. 已奏效的做法及迁移范围

| 做法 | TS 中的实际落点 | 对 Go 的启发与限制 |
| --- | --- | --- |
| 删除无用热路径工作 | 删除 `write_ff` 中未使用的逐字节调试字符串；常见类型直接判断，取消临时参数对象 | 先找可证明冗余的工作，再增加复杂算法；检查重复反射、取值、转换和临时切片 |
| 稳定信息在初始化时确定 | schema/elementType 复用，低 tag 用最多 128 项索引，稀疏 tag 继续 Map | 复用现有 Go 元信息，预绑定类型事实；数据、预算、presence 和布局不能跨调用缓存 |
| 预检与写出职责分开 | 数组先完整校验安全整数、宽度和尺寸，写出再用 4/8 字节 DataView 循环 | 复用已验证的信息，减少重复解释；不能删掉预算、值域或窄化检查来提速 |
| 专用字节操作代替通用接口成本 | 缓存 DataView，绑定真实 byteOffset/byteLength，扩容后失效 | 测标准库小函数的内联与边界检查消除；TS DataView 的优势不等于 Go 中也要引入新视图 |
| 批处理已经确认的连续块 | FF 段有界原生扫描、批量复制；扫描门槛从 1024 B 调整到已验证的 64 B | 连续内存可批处理，混合 word 保留便宜路径；64 B 是 TS 的参数，不是 Go 通用常数 |
| 消除调用内中间复制 | pencode/attach/Response 在 scratch 中接续写出，最后返回独占 packed 字节 | 优先融合真实调用链；公开 Encode 的独占结果与内部同步借用要分开，不能偷换调用入口 |
| 复用私有同步工作区 | pdecode/dispatch 有界复用解包缓冲，公开 unpack 仍独占 | 先证明解码结果不保留借用视图，再考虑复用；当前 Go API 和失败原子性必须保持 |
| 根据字节形态选择策略 | 公开 unpack 仅在最多八段中 FF 字节已覆盖 packed 输入四分之三时精确预扫 | 消息大小不足以决定算法；Go 已有精确分配，不重新照搬 TS 的预测容量策略 |
| 小幅展开，保留尾部和额度检查 | 连续零头四个一组计数，剩余逐字节处理 | 以零段长度和混合输入验证收益；Go 的零初始化与编译器行为不同，需重新测量 |
| 段状态留在段循环 | FF 合并集中到 Pack 主循环，普通混合 word 跳过段收尾 | 缩小每个 word 的工作，不按消息名称或特定 mask 特判；同时测内联预算和已有 FF 快路径 |

这些收益分布在不同版本、输入谱和调用入口，不能把各轮百分比连乘成一次累计提速。源码、原始值和取舍分别在 [初轮优化](benchmarks/2026-10-15-optimized/RESULTS.md)、[长块切片](benchmarks/2026-10-15-sproto-next/RESULTS.md)、[第二轮](benchmarks/2026-10-15-sproto-round2/RESULTS.md)、[第三轮](benchmarks/2026-10-15-sproto-round3/RESULTS.md)、[第四轮](benchmarks/2026-10-15-sproto-round4/RESULTS.md) 和 [第五轮](benchmarks/2026-10-15-sproto-round5/RESULTS.md)。

## 5. 失败尝试比代码技巧更值得保留

| 尝试 | 已观察到的问题 | 后续规则 |
| --- | --- | --- |
| 大包一律预扫并精确分配 | 第三轮大型游戏/整数数组公开 unpack 约慢 36%，组合解码也回退 | 少一次分配未必抵得过扫描；检查完整路径而非只数 alloc |
| 看到长 FF 前缀就预扫 | FF 前缀后接稀疏数据可慢约 25%–39% | 输入必须包含快路径前缀加昂贵尾部，不能只用纯 ASCII |
| 原生比较长零块 | 纯零很快，重复 9–33 个零 word 却可慢一倍以上 | 统计失败探测成本；确认长段前不要反复调用较重的原生操作 |
| 预清零输出后只写非零字节 | 数值解包改善，但 ASCII 约慢 18% | 初始化成本属于总成本；Go 新分配内存本就清零，不能类比 Buffer.allocUnsafe |
| 无分支写出、先算 mask、双字节查表 | 第四轮大型/整数 Pack 反而更慢；双字节表另占 256 KiB | 分支少不等于指令少；同时统计额外写入、查表、缓存和内存代价 |
| 四字节 SWAR、小表/DataView、switch 压紧 | 第五轮没有稳定的完整消息收益 | 不因 C 或某个微基准适用就推断 JS/Go 适用；按当前编译器重新验证 |
| 游标、预加载、短循环改写 | 部分输入改善，其他输入回退，没有稳定优势 | 保留较直接的实现；代码形状本身不是优化成果 |
| 精确长度时省去 subarray | 专项有收益，完整短零段形态仍回退；公开和私有候选均撤回 | Buffer 子视图不是字节复制；不能把少一个对象当作必然加速，也不能据此推断 Go 切片表现 |

第五轮还暴露采样顺序的影响，部分候选回退与 V8 内部机制的因果关系没有定论。记录“候选未通过验收”即可，不将未知原因包装为确定的 JIT 结论。失败值与复核值保留，不以专项较好的结果覆盖全量结果。

## 6. Benchmark 和 profile 的经验

### 输入必须同时固定语义、形态与构造方式

- 共用 AddressBook、两档游戏状态、896 项数组及 Echo 夹具，固定 raw/packed 签名和 padding；PB 数组使用现有 packed/sint32，presence 契约继续保留。
- 同值不等于同运行时输入。分别 repeat 的 4 KiB 字符串，在 V8 中可能分别为平坦字符串和拼接字符串，编码源码相同仍出现数倍耗时差。已改为准备期只构造一次，让 PB/SP 共享输入；旧 Echo 编码百分比不能不加说明地复用。
- Go 对应要区分复用对象与每次新建、指针和值、nil/空、原生与命名类型、对象修改后重编码。编码输入不能在计时中悄悄变更，旧返回值也不能因下一次操作变化。
- 正确性用完整 int64 边界保护；跨语言性能夹具仍用双方都能准确表达的数据。不要让 TS 精度限制悄悄缩小 Go 的契约。

### 调用入口必须相同

分别记录纯 Encode/Decode、Pack/Unpack、分阶段组合和真实 pencode/pdecode/attach/dispatch。手工拼帧包括中间输出、concat、已知 schema 切分等成本；原生路径可融合这些步骤。把旧手工数据换成新原生数据，不能算同一路径优化。

公开输出分配、内部热缓冲和冷启动分别观测。编解码器测试不包含的网络、MAC、会话分配和外层预检必须标明。PB/SP 使用同语义数据，但 wire、反射和失败原子性成本不同，既不能删检查求公平，也不能把实现差距全归因于协议格式。

### 采样与源码必须绑定

- TS 最终按操作名将 PB/before/after 紧邻采样，奇数轮整体反转；独立热身和五轮原始值全部保存。整组版本顺序更易受时间、GC 阶段影响。
- Go 前后版本用各自固定二进制配对并交替先后，保持相同 GOMAXPROCS、工具链、夹具和参数；不能将两个包版本装进不同调用链后直接排名。
- 计时、CPU、分配 profile 和测试顺序运行；保存 commit、实际模块覆盖、编解码源文件哈希、脚本、生成物/夹具和环境指纹。GSR 正式 require 与临时 modfile 必须分开记录。
- 五轮中位数便于描述，不等于显著性证明。超过 10% 的回退用于触发排查，不表示小于 10% 自动可接受；持续的小包损失、额外内存和真实调用成本都要评估。
- max/min 明显波动时，先查 PB 控制和运行条件，再保持源码不变复核；复核保留原始全量，不挑最好一轮或反复重跑直到过关。

### Profile 回答热点位置，不直接给出收益

独立 Pack 时间除以 PEncode 时间，不等于真实 CPU 占比。第五轮另外采真实 pencode：整数数组的 Pack 累计样本约 73% → 70%，大型游戏状态约 27% → 29%。同一策略在两个场景中的收益上限不同；大型消息其余编码仍占主要部分。

self/cumulative 存在包含关系，不能相加；占比随总耗时分母变化，不能相减推算绝对提速。V8 的 inlined 代码也可能归因到调用者；原 pack_seg 已可内联，不能看到 helper 名字就认定函数调用开销。Go 应看当前编译器的内联、逃逸和边界检查诊断，而不是根据函数长短猜测。

显式 Buffer 工厂/subarray 调用数不是完整对象分配统计，V8 sampled heap 不完整覆盖 Buffer 外部内存。Go 同时记录 ns/op、B/op、allocs/op、alloc_space/alloc_objects；还要报告缓存保留和并发实例总成本。TS 16 KiB 工作区在一万个实例均达到上限时仅该项就约 156.25 MiB，少分配与少保留内存是两回事。

## 7. 后续 Go 的验证矩阵

优先复用独立库已有测试，GSR 只保护接线和跨语言行为，不复制底层整套夹具。

| 维度 | 需要继续保护的输入/行为 |
| --- | --- |
| wire | 独立官方 raw/packed、全部 mask × 高位非零值、FF 起止/256-word、六/七字节合并、尾部、不对齐视图 |
| 字段与数值 | 缺失/零值/presence、nil/空数组、原生/命名类型、首/中/尾宽值、负数、未知/高 tag、double 位模式与整数溢出 |
| 资源与失败 | 默认及自定义额度的临界值、深层/超元素输入、迟到截断、schema 构造失败、解码错误后原值不变 |
| 状态与输出 | 同一对象修改后重编码、旧输出独占、大小包交替、失败后复用、大包不抬高长期保留容量、已有并发契约 |
| 性能形态 | 32 B 小包、UTF-8、4 KiB ASCII/零、不同非零字节密度、随机数据、FF/零前缀接稀疏尾部、重复短段 |
| 集成 | 现有官方对照、有限 fuzz、库 race/vet，以及临时依赖下 GSR Sproto Dispatcher 与 Plain/MAC Echo |

Go offset 访问的后续回归说明：字段属于当前 schema，不等于实际嵌套 Go 值具有该 schema 的布局。公开父描述被替换时，两者可能分离；验证矩阵需覆盖根字段替换、子描述替换与子 schema 内字段替换。校验可在同构数组入口复用，但必须依赖实际类型事实，不能把安全检查移出循环后静默取消。正确性修复与加速同时发生时，分别报告上一提交和最小修复版对照，保留必要校验的成本。见 [Go 实例](benchmarks/2026-10-16-gosproto-bindings/RESULTS.md)。

14 种 Pack 和 46 种 Unpack 形态来自 TS 的回退排查，不是 Go 已覆盖数量。将其中缺失且相关的形态补入现有 Go Benchmark 后，才报告 Go 的覆盖情况；不要求不加区分地复制所有 TS 微基准。

## 8. 转入 gosproto 的下一步

具体路线继续由 [Go 优化方案](RFC-GOSPROTO-PERFORMANCE.md) 管理，本文只给可执行的准备顺序：

1. 固定 TS `9801808`、Go `6012b06` 和当前 PB 版本，核对独立库工作树与实际模块选择。从当前 Go 实现重建 Encode/Decode/Pack/Unpack、完整组合与小帧的基线，记录分配；正式 v0.4.0 保留为历史对照。
2. 分开采当前 game_large、int32_edges、AddressBook 和 Echo 的 CPU/分配 profile，再选择最大可消除成本。TS 的 Pack 优先级不能直接移植给 Go；反射、encodedSize、字段访问、reflect.New 和 packing 都需要当前证据。
3. 优先在现有元信息和安全 Go 路径中减少重复解释、取值和遍历。专用函数是否阻止内联、类型断言是否导致逃逸、布局记录是否增加分配，都用当前编译器与真实消息核对。
4. 一次只做一个可归因的纵向切片。若主要瓶颈已转向不可轻易消除的 optional/独占对象分配，先说明实际代价；不自动换成值字段、共享对象、池、unsafe 或 generator。
5. 每步同时给出收益、无改善、回退和内存代价，最后重跑现有 Go/TS × PB/SP 两套完整基准。TS 未改时作为控制，不把它的噪声算成 Go 收益。发布、升级依赖仍单独处理。

目标是检验同一 Sproto wire 下 Go 实现的改进空间，而不是预先承诺全面超过 Go Protobuf。TS 的结果证明实现选择能显著改变结果；是否能在 Go 重现同样曲线，必须由 Go 自己的基线、profile 和验收回答。

上述流程已在 [Go 第三轮](benchmarks/2026-10-16-gosproto-round3/RESULTS.md) 执行：解包展开、固定窗口和原生指针直接赋值都没有通过完整收益筛选，不能因为 TS 曾受益就保留。当前只收窄了有界布局记录的存储宽度，取得确定的内存收益，CPU 基本持平。这也是经验迁移的边界：迁移验证方法，不承诺迁移同一段代码后的收益。

[大型 Encoder 切片](benchmarks/2026-10-16-gosproto-encoder/RESULTS.md) 进一步验证：缓存操作码却增加解释/函数层并没有自然获得速度，候选被撤回；绑定实际 Go 字段位置并只读访问原生 `*int64` 才显著减少大型编码成本。普通 struct、命名类型、预算和输出所有权继续成立，公开元信息变化要求 owner/形状检查。这些检查有真实小包成本，不能为了排名删除；需要同时披露每调用分配、一次性元信息与完整帧收益。
