# 一万个 Service 混合 Send 负载验证

## 已确认的场景

用户确认总量同时包含本地和跨节点业务请求，第一轮全部使用 Send，不包含 Call/Reply、数据库、业务 I/O 或逐条日志。

| Service 数量 | 每 Service 速率 | 总速率 |
| ---: | ---: | ---: |
| 7,000 | 0 | 0 |
| 2,000 | 1/s | 2,000/s |
| 800 | 5/s | 4,000/s |
| 180 | 10/s | 1,800/s |
| 20 | 100/s | 2,000/s |

合计 9,800/s，本地 80%（7,840/s），跨节点 20%（1,960/s）。正式阶段 180 秒，共 1,764,000 条，其中本地 1,411,200 条、跨节点 352,800 条。另有 5 秒预热，共 49,000 条，不计入正式延迟样本。

## 测试实现与限制

入口为 `examples/twonode/mixed_load_test.go`，仅在 macOS/Linux 编译。目标测试进程创建全部 Service；独立子进程通过真实 TCP 连接目标的 `127.0.0.1` 临时端口。子进程不 Open，不设置来源节点身份；借用受信任 Cluster client 作为负载生成器，不宣称覆盖业务 Service 发起远端调用的组装。

- 使用默认 Mailbox 和 Cluster 队列容量，不扩大队列或重试失败请求。任何 admission 错误均失败，最终检查 Runtime admission 拒绝计数及 Cluster 诊断。
- 100 个 10ms 时隙组成一秒，各 Service 按自身频率选时隙、按索引错开相位。每五条中的一条走远端，选择位置随 Service 错开；每个完整五秒窗口严格满足 80/20，不要求每个时隙比例都相等。
- 两端使用同一主机上的未来开始时间。按绝对时刻发送；调度迟到时会处理已到期时隙，记录最大迟到值。因此必须检查生成器延迟，不能只凭平均速率忽略追赶形成的短突发。
- Handler 仅更新自身计数、核对各路径连续序号并记录延迟。不要求本地和远端两条独立路径之间保持全局顺序。
- 延迟从实际调用 Send 前到目标 Handler，包含远端编码、TCP 和入站投递，不含生成器迟到；跨进程使用同机墙钟，不能直接搬到未同步时钟的多机测试。
- 各活跃组分别报告 P50/P95/P99/最大值。预分配每 Service 的样本容量，整个测量保留正式阶段约 14.1MB 的 duration 数据；测试夹具自身的内存、分配和共享计数器成本必须计入解释，不能当作纯 Core 开销。
- 每十秒打印目标进程 RSS、Go 堆、GC 次数、goroutine 总数和处理累计数；正式阶段记录 CPU 时间折合平均使用核数、累计 GC 暂停和分配增量。CPU/RSS 包含本地发生器、采样及 TCP 入站，不包括独立发送进程，不是逐物理核利用率。
- 用 Go `schedtrace` 采样全局与各 P 的 runnable 队列，不能拿 goroutine 总数代替 runnable。它只是离散采样，可能漏掉短峰值；不包含当前正在执行的 goroutine。
- 发送完成后等待最终总数，再关闭 Runtime；逐 Service 检查处理数、序号、样本数，检查 PendingCall/Timer 清理及 Closed 状态。Send 返回 nil 本身仍只代表本地接纳，最终计数是测试证据，不改变 Send 协议。

## 执行步骤

先短跑验证组装、计数和清理：

```sh
GSR_MIXED_LOAD=1 GSR_MIXED_SECONDS=5 go test ./examples/twonode -run '^TestMixedServiceLoad$' -v -timeout=1m
GSR_MIXED_LOAD=1 GSR_MIXED_SECONDS=5 go test -race ./examples/twonode -run '^TestMixedServiceLoad$' -v -timeout=1m
```

短跑通过后正式测量。先编译再设置 GODEBUG，避免把编译器的调度输出混入目标进程；子进程主动清空 GODEBUG，防止混淆两个进程的调度行。

```sh
mixed_dir=$(mktemp -d "${TMPDIR:-/tmp}/gsr-mixed.XXXXXX")
go test -c -o "$mixed_dir/twonode.test" ./examples/twonode
GSR_MIXED_LOAD=1 GODEBUG=schedtrace=1000 "$mixed_dir/twonode.test" \
  -test.run='^TestMixedServiceLoad$' -test.v -test.timeout=4m \
  > "$mixed_dir/run.log" 2>&1
```

180 秒是用户明确要求的专项负载预算，不扩展普通测试门禁；默认测试跳过此场景。正式性能结果不用 race 采集。`run.log` 中 SCHED 行的 `runqueue` 加末尾各 P 队列长度可得到采样时的等待运行数量；`gomaxprocs-idleprocs` 不是 CPU 利用率，不能混用。

## 当前状态

2026-09-15 首两次短跑在进程启动前被权限审核服务的容量故障阻止。用户恢复权限后，5 秒短跑、5 秒跨进程 race 和首轮三分钟正式测量均通过；没有修改生产实现、扩大队列或重跑挑选更好样本。生产版本为 `2d13014`，另有本轮未提交测试夹具。环境 Go 1.23.3、darwin/arm64、Apple M2、GOMAXPROCS=8，普通开发机，同机 TCP。

## 三分钟正式结果

正式测量耗时 179.998680 秒，实际平均输入 9,800.07/s。正式阶段处理 1,764,000 条；加预热后本地尝试 1,450,400 条、远端尝试 362,600 条，目标共处理 1,813,000 条。每 Service 的计数、各路径序号、正式样本数与最终清理全部通过；MailboxFull、Handler error 和 Cluster 诊断均为零。

| 每 Service 速率 | 正式样本数 | P50 | P95 | P99 | 最大 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1/s | 360,000 | 66μs | 309μs | 1.080ms | 40.597ms |
| 5/s | 720,000 | 69μs | 393μs | 1.242ms | 34.390ms |
| 10/s | 324,000 | 49μs | 335μs | 963μs | 34.052ms |
| 100/s | 360,000 | 34μs | 305μs | 874μs | 44.806ms |

- 目标进程平均使用 **0.0476 核**，即单核约 4.76%，不是整机 CPU 4.76%，也没有测量逐物理核利用率。独立远端发生器 CPU 未计入。
- 输入阶段 GC 12 次，累计暂停 1.416917ms，分配增量 309,680,408B（约 1.72MB/s）；Go 堆从 36,107,272B 到 43,954,304B，中间随分配/GC 呈锯齿变化。
- 每十秒 RSS 样本为 53,616～86,960KiB（约 52.4～84.9MiB）；20～140 秒多数约 77～79MiB，150/160 秒升高，170 秒下降。没有持续单调增长证据，但三分钟不足以排除慢泄漏。RSS 包含样本存储及其它夹具成本，不等于 Runtime 独占内存。
- goroutine 十秒采样为 10,009～10,010，大部分为 10,009；不能把短暂多一个 goroutine 解释成泄漏。
- 取进程启动后约 8～188 秒（排除启动和预热）共 179 条 SCHED 样本，等待运行队列总数均值 2.073、最大 73、11 次非零。该值为全局队列加各 P 本地队列，不含正在运行者；每秒采样可能遗漏峰值，也不能证明全程没有短积压。
- 两端发生器最大迟到均为 72.819ms（该指标覆盖预热及正式阶段）。平均速率达标不等于均匀输入；迟到后的追赶批次、墙钟计时和轻量调度采样均属于本次测量限制。未采集能归因这些尖峰的完整 trace，不猜测具体根因。

每十秒观测的累计处理数与计划累计量相符，最终无丢失、重复或资源清理失败；这支持当前最小 Handler、同机 TCP 和给定规模下的运行模型。**可以暂不优化 Scheduler，将研发重点转回 Cluster 正确性、生命周期、故障隔离及业务迁移。** 但 CPU 远未饱和，不能用本轮结果证明重计算的多核线性扩展；业务尾延迟门槛尚未给定，也不宣布真实游戏业务或生产内网容量已验收。

原始调度与测试输出本轮保存在 `/private/tmp/gsr-mixed.tfYSy3/run.log`，临时目录不保证长期保留；复测使用上文命令。短跑非 race 和 race 均处理 98,000 条（含预热），不将 race 的 CPU/RSS 与正式性能混用。
